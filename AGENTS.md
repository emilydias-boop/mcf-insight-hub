# Architecture rules

- Pós-Venda recurring manager availability lives in pos_venda_disponibilidade and uses São Paulo slot starts; booking validation only applies to configured managers in pos_venda_reunioes, preserving the separate closer agendas and unconfigured managers.

- Revenue summaries classify portfolio payments by period-wide deduplicated gross per existing sale identity before row attribution, so all grouping modes preserve attribution and share the same new-sale boundary.

- Commercial team dashboards share their filter bar and KPI-card renderer; BU-specific data and table columns stay in dedicated page/table adapters to preserve each BU's business rules.- BU Pós Venda is isolated by its single origin id (`POS_VENDA_ORIGIN_ID` in src/lib/posVenda.ts); its stage-deliverable lock is a crm_deals trigger with a WHEN clause on that origin, so other pipelines never run it.
- Pós Venda new-sale ingestion is a hubla_transactions trigger (pos_venda_on_venda → pos_venda_registrar_cliente), so every source (Hubla, Kiwify, MCFPay) is covered without editing webhook handlers; failures are logged to pos_venda_entrada_falhas instead of blocking the sale. A client who already has a card in the BU keeps that card and the sale is only appended to pos_venda_compras (matched by lower(email) or 9-digit phone suffix + first name); a new card is created only when the client has no Pós Venda card.
- Manager distribution for Pós Venda lives only in pos_venda_distribuicao and is applied only inside pos_venda_registrar_cliente, so other BUs' lead distribution is never affected.
- Leaving the "Novos licenciados" stage requires a recent pos_venda_nota_contato activity, enforced by a crm_deals trigger scoped to the Pós Venda origin; client BU movements are logged to crm_cliente_timeline for the future timeline screen.
- Contact freshness for Pós-Venda is derived by kanban_resumo_lote and mirrored in kanban_filtrados; card/header share estadoContato and legacy summaries reuse the RPC, so missing evidence cannot fall back to a call timestamp. Other origins retain their existing semantics.

- Front-end telemetry (errors, page views, page load time) goes only through src/lib/telemetry.ts into app_telemetry, fire-and-forget, so a logging failure never blocks a screen.
- Manual Academy track assignment uses the admin/RH-validated academia_atribuir_trilhas RPC; additional tracks reuse extension records and expose every assigned phase, preserving existing tasks and progress.
- Process materials library (processos/processo_etapas/processo_materiais) is display/edit-only: it never feeds automation_templates or any sending path; /pos-venda/fluxo injects it as window.__MATERIAIS__ and falls back to the HTML's embedded data.
- Flow document dialogs live outside the sandboxed iframe; accept material messages only from its contentWindow and queried material IDs, and keep dialog state independent of flow refetches.
- Script Piloto pilots are derived on read by script_piloto_reunioes (R1 completed, 2–3 unrefunded paid attendees), so they enter and leave automatically without a table or job; AI-generated drafts are never stored and only become official through script_publicar_versao.
- Weekly closer summary is sent only by the resumo-semanal-closers edge function (Monday cron), deduplicated per week+BU in resumo_semanal_closers_envios, so re-runs never double-send.
- CRM timeline, notes, and call history share presentation-only recording and note renderers under timeline/; data fetching and mutations stay in their original hooks so legacy tabs keep their behavior.
- Deal drawer contact logging goes only through the registrar_contato RPC (src/components/crm/drawer/); next-action reminders come from the DB cron, so the front end never inserts into alertas for them.
- CRM Overview classifies stage moves via src/lib/crmStageClassification.ts (metadata.to_stage_id > UUID to_stage > name resolved in crm_stages), because trigger rows store stage names.
- Consórcio "Relatório da Cota" reads only through consorcio_relatorio_cota (shows only recorded data, never recomputes); outbound delivery to HARVEY goes only through the harvey-relatorio-cota edge function, logged one row per card+month in consorcio_harvey_envios to avoid duplicate sends.
- Agenda grids/lists read briefing only via the batched useBriefingsResumo (one query per screen); full BriefingLeadCard/ResumoAnamneseCard mount only inside meeting details via MeetingBriefingSection, to avoid per-card fetches.
- Daily presence/capacity is derived on read by capacidade_dia/equipe_agora from page_access_log plus leader corrections (presenca_correcoes); person exceptions live only in presenca_config_pessoas, so closer/sdr records are never edited for capacity rules. FinanceHub reads them only via the external-query whitelist.

- Pós-Venda journey uses jornada_calcular for both the read-only deal card and public consultar-jornada, deriving phase from jornada_mapa_estagios and recorded deal_activities; CPF matching/fill is isolated to the Pós-Venda origin, preserving webhook ingestion and other BUs. Legacy jornada_etapa_atual_id/jornada_eventos remain stored but unused, so historical data is retained.
- Hiring/termination governance reuses employees/departamentos/cargos_catalogo; hierarchy is resolved only by gov_* SQL functions (cargo reporta_a → current occupant via employee_cargo_historico, fallback employees.gestor_id) so all phases share one source of truth. Approval-rule (alçada) writes are restricted to admin/rh.
- Hiring requisitions freeze at submission through a database trigger and store prospective actors from gov hierarchy/alçadas; approval decisions remain unavailable until the shared signing engine exists, preventing unsigned approval bypasses. Privileged request-option helpers live in gov_private behind invoker API wrappers.
- Employee dossiers use gov_dossie_registros with database-enforced 24-hour immutability and linked addenda; acknowledgments are separate immutable records, attachments use a private record-scoped bucket, and legacy notes/PDIs/flags remain read-only in this view without altering their existing flows.
- Org-structure screen (/rh/estrutura) reads only via gov_estrutura_em (safe subset, salary bands RH-only) and builds hierarchy client-side in src/lib/estruturaOrg.ts; edits go only through gov_* wrapper RPCs backed by gov_private, with cycle-guard and audit_logs triggers on departamentos/cargos_catalogo/employee_cargo_historico.
- Termination requests write only through gov_private-backed RPCs, enforce employee self-exclusion even for RH, freeze on submission and preserve employees unchanged; suggested-signatory removals require separate RH validation and the RH role cannot be removed. Decisions await the shared signing engine.
